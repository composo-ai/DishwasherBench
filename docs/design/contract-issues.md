# Known problems in the simulation design contract and its typed skeletons

> **Record of the build, kept as written (9 October 2026).** A list of defects found in
> `sim-core.md` and in the first typed skeletons, before the packages were built. It has not been
> brought up to date entry by entry, so an entry may since have been fixed. The current state of
> the simulation is in `scope.md` and `docs/validation/README.md`; the index of the documents is
> `docs/README.md`.

`sim-core.md` was transcribed into typed package skeletons (packages `sim-*`) on 2026-10-09 and the result was reviewed against the contract. This file records what the transcribing engineer found wrong or missing in the contract itself, and what the reviewer found wrong in the skeletons. Nothing here has been fixed centrally. The engineer who builds a package fixes the entries that concern it; `scope.md` says the skeletons are a starting point, not frozen interfaces.

Paths beginning `scratchpad/` name the reviewers' working files, which are not in the repository.

## Reviewer findings on the skeletons

The transcription is faithful, but the skeleton is not ready for thirteen engineers: two conventions it fixes are wrong, and the modules cannot yet agree on how to address each other's records.

**What holds up.**
- **Completeness.** All 71 types of the contract's code blocks exist under their own names; `wash` exists only as the type `Wash`, as reported. `LineElement` and `LoadManifest` are absent, also as reported. 53 exported type names are invented helpers (listed by `completeness.mjs`, a working script that is not in the repository).
- **Fidelity.** A type-level comparison of every declaration and top-level member against the contract's own code blocks (998 assertions) finds only the four deviations the engineer reported: `i16` in `FieldDef`, the added `TierParams` fields, `SceneContact`, and `RigidCouplerPort`. Every method the contract makes asynchronous returns a Promise. 775 nested member names and optionality marks match.
- **Layouts.** All 40 pass the layout rules. The 37 I transcribed independently match in size and offsets. No narrow field has a state or accumulator role; the narrow evolving fields (regime, wet flag, layer count, fill fractions) follow the contract's own tables.
- **Dependencies.** package.json equals the table plus core, the graph is acyclic, and sim-gpu depends on core alone.
- **Hygiene.** All 332 exported symbols and 834 members have doc comments; there is no `any` and no default export in sources.
- The engineer's contract issues that I checked are accurate.

**Root commands.** `pnpm typecheck`: every project Done, no errors. `pnpm test`, first run: "Test Files 1 failed | 93 passed (94), Tests 1 failed | 1888 passed (1889)"; the failure was `@spotless/machine` `src/validate.test.ts`, another team's file in flight. Second run ten minutes later: "Test Files 94 passed (94), Tests 1892 passed (1892)". Simulation packages alone: 18 files, 368 tests passed.

**What is wrong.** Two findings should be fixed before the build starts, because they will otherwise diverge silently across modules:
- **Arm rotation.** The invented sign convention contradicts `@spotless/machine`, no type maps a phase to an angle, and the owner's lower arm turns clockwise.
- **Soil class.** It is frozen to the 8 mechanism classes, which cannot key the contract's per-soil parameter tables, and it lives in a package the liquor model and the registry cannot import.

The majors are mostly contract gaps the transcription copied without flagging:
- The Bosch roof sprayer, fed half the time, has no representation in arm-only types.
- Addressing between modules is undefined: JetExposure tiles, the EffectiveExposure grid, S-cell indices, and ping-pong buffers handed over as single handles.
- The rigid port drops contacts and events.
- Buffer handles go stale on every evict/readmit, with no way to renew them.
- Several result fields have no producer.
- The tracer has no way to pose the arms.
- `PhaseEvent` cannot carry pre-store fills.
- BlockRelease saturates within the admitted soil range.
- The star re-export scheme makes one flat namespace: a name clash breaks typecheck in a third engineer's package.
- No stage has a factory (reported by the engineer, still open).

**Boundaries.** The machine stand-in is minimal and clearly marked, but lacks the arm sense and a sump region. The physics additions are named correctly but underspecified on snapshots and on what `contactWrench` returns against static bodies. The catalogue comment corrections are precise and correct.

### R1 [blocker] `packages/sim-hydraulics/src/types.ts`

**Problem.** Arm rotation is defined against the platform package it wraps, and nowhere is a phase mapped to an angle. `ArmMotion.omega_rad_s` is documented as signed about tub +z (counter-clockwise positive), and `RigidResult.arms[].meanOmega` is 'signed as ArmMotion.omega_rad_s'. The machine package, which M4 must call, uses the opposite convention: speed is non-negative in the arm's own sense and a clockwise arm's angle decreases. The stand-in `MachineGeometryPart.arm` has index, hingePoint and hingeAxis but no rotation sense. `posArm`/`dirArm` are 'in the arm frame' with an invented '(z along the hinge axis)' and no origin or x axis. `ArmState.angleQ` and the u32 phase have no stated direction. M3 (arm ray instances), M4, M5 (launch velocity), M6 (arm obstacles, phase bins) and M11 (torque balance) all need one mapping; as typed they will mirror clockwise arms differently.

**Evidence.** packages/sim-hydraulics/src/types.ts:80-85 ('about the +z axis of the tub frame (positive counter-clockwise...)... The contract gives no sign convention'). Header of packages/machine/src/kinematics.ts: 'a clockwise arm's angle decreases with time. The arm speed omega is in the arm's own rotation sense (positive when it turns the way SprayArmSpec.sense says)'. Contract M4: 'steady, free: w = ..., clipped at 0' and 'omega_rad_s /* mean; 0 when stalled */', i.e. a magnitude. The owner's machine has a clockwise lower arm (`sense: 'cw'` in packages/machine/src/data/bosch-smv4hax40g.ts) and a counter-clockwise upper arm; SPOT-60 has one ccw and two cw. packages/sim-scene/src/machine-boundary.ts:50-57 (no sense). packages/sim-rigid/src/types.ts:76-77 and contract.test.ts:96 (fixture `meanOmega: -3.14`).

**Suggested fix.** Adopt the machine package's convention in every doc comment: omega >= 0 in the arm's own sense, and the phase advances in that sense. State once, beside PHASE_UNITS_PER_REV, that the angle of kinematics.ts is angle(phase 0) + senseSign x 2 pi x phase / 2^32. Add the sense to `MachineGeometryPart.arm` (or define hingeAxis as the rotation vector by the right-hand rule). Define the arm frame of posArm/dirArm by reference to `nozzleState`. Correct meanOmega, armTorqueBalance, angleQ and the -3.14 fixture.

### R2 [blocker] `packages/sim-soil/src/types.ts`

**Problem.** 'Soil class' is frozen to the wrong code space and lives where two of its users cannot import it. (1) `SOIL_CLASS_IDS` is the 8 mechanism classes SOL..PART, and its position is made the code of `SoilCell.class` and the index of `RateTables.aT`/`sfc`. The contract's per-class tables are the rows of soils 8.1 to 8.3, which are soils, several per mechanism class. With 8 codes the kernel cannot give dried egg yolk, egg white and cheese (all SWP) different lag, rate and activation energy, and the ten soils of soils R4 collapse. (2) M9 builds `aT`/`sfc` 'indexed by soil class' and M2 holds `soil.<class>.*`, but the list is in sim-soil, which neither may import. (3) `WashResult.soilClasses` is a third notion (appearance classes) that the code does not distinguish.

**Evidence.** packages/sim-soil/src/types.ts:24-41 ('The position of a class is its code in SoilCell.class and its index in the per-class arrays of RateTables'). packages/sim-params/src/shared.ts:268-271. packages/sim-liquor/package.json depends on core and sim-params only. Contract M8: 'The per-class tables of soils 8.1 to 8.3 are the registry content for soil.<class>.*'; 'soil.<class>.JOHref ... (egg yolk)'; 'per class (9 min egg yolk at 50 C)'; 'C_ad = 1 for starch against ... ketchup'. docs/research/soils.md 8.1 has 17 rows keyed by soil with a Class column; section 7.9 has the 8 classes. docs/research/standards.md 10.3 lists four appearance classes. packages/sim-core/src/contract.test.ts uses soilClasses ['protein','starch'].

**Suggested fix.** Declare the vocabulary in sim-params, the lowest module M2, M8, M9 and M12 all reach, and name three things apart: mechanism class (SOL..PART, a property of a parameter set), parameter class (smallest reading: one per catalogue soil id, `soil.<soilId>.*`, the rows of soils 8), and appearance class (the result). Make `SoilCell.class` and the per-class arrays of `RateTables` index one ordered table of parameter classes that both `SoilStage.init` and `LiquorModel.rateTables` receive, for example the sorted distinct `ItemSoilRecord.type` of the load. Say so in both doc comments.

### R3 [major] `packages/sim-params/src/shared.ts`

**Problem.** Machine boundary: the owner's machine has a spray level the types cannot represent. `MachineSpec.sprayLevels` is `SprayArmSpec | FixedSprayerSpec`; the Bosch has a fixed roof spinner whose spray is a droplet shower, 'not coherent jets'. Every simulation type is arm-only: `ComboId.arms` ('one per arm fed'), `HydraulicPoint.arms` and `nozzles[].arm: number`, one `EmitterTable`/`DepositionTable`/jet-wet table per arm binned by that arm's phase, and six `SOURCE_KIND_CODES` with no sprayer. 'Index of the arm in the machine's arm list' is also undefined, because the machine has no arm list, only string-id spray levels: is it an index into sprayLevels or into the arms among them? The engineer imported MachineSpec and did not report this.

**Evidence.** packages/machine/src/types.ts: `FixedSprayerSpec` ('Its nozzles describe the outlets for the hydraulics; its spray is described by `spray`, not by coherent jets'), `SprayLevelSpec`. packages/machine/src/data/bosch-smv4hax40g.ts: `kind: 'fixed', id: 'roof', type: 'free_spinning_rotor', spray: { pattern: 'rotating_shower', coneHalfAngleDeg: 65, dropletSpeed: 2.5 }`; diverter positions `r` (roof only) and `ur` (upper + roof). packages/machine/src/data/bosch-programmes.ts: BOSCH_PATTERN_60 = [['l', 60], ['ur', 60]], so the roof sprayer is fed for half of all circulation. packages/sim-params/src/shared.ts:80-81; packages/sim-hydraulics/src/types.ts:76-77, 113-114; packages/sim-jets/src/layouts.ts SOURCE_KIND_CODES.

**Suggested fix.** Decide and document the smallest reading, then report it as a contract issue. For example: `arm` is the index into `MachineSpec.sprayLevels`; a fixed level appears in `ComboId.arms` as a level with one constant phase; its shower enters M6 as source records of an added kind with cone half-angle and droplet speed from the spec, in a one-bin table like a stalled arm's. State the mapping in ArmMotion, NozzleJet, the stand-in and SourceRecord.

### R4 [major] `packages/sim-scene/src/exposure.ts`

**Problem.** Element addressing on the frozen interfaces between modules is undefined, so writer and reader will index differently. (a) JetExposure: 'tiles of 8 x 8 soil cells' and '64 records per allocated tile, in the soil-cell order of the tile' do not say which cells form a tile or in what order; M5 writes and M8 reads.
